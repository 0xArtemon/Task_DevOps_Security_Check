# Security Check Script (`security_check.sh`)

Автоматизований Bash-скрипт для проведення базового security-аудиту Linux-сервера перед розгортанням production-проєкту. Скрипт збирає ключові метрики безпеки, формує структурований звіт із кольоровою індикацією ризиків у терміналі та зберігає чисту текстову копію у файл `security_report_YYYYMMDD_HHMMSS.txt`.

## Структура скрипта

Скрипт побудований модульно і складається з таких основних частин:
1. **Ініціалізація та обробка аргументів** — налаштування ANSI-кольорів, парсинг прапорців `--quick` / `--full` та ініціалізація лічильників ризиків.
2. ** Інформація про систему** — збір базових даних про ядро (`uname`), хост, аптайм та дистрибутив (`/etc/os-release`).
3. ** Користувачі та автентифікація** — перевірка прав поточного користувача (`id`), дозволів `sudo -l`, пошук прихованих суперкористувачів (`UID = 0` у `/etc/passwd`) та аудит останніх входів (`last`, `lastb`).
4. ** Права доступу до файлів** — пошук SUID/SGID-бінарників, файлів із правом запису для всіх (`-perm -o+w`), а також перевірка Linux Capabilities (`getcap` у режимі `--full`).
5. ** Мережа** — аудит активних слухаючих портів та встановлених з'єднань за допомогою `ss` (з резервним переходом на `netstat`).
6. ** Процеси та автозапуск** — вивід дерева процесів (`ps aux --forest`), перевірка користувацького `crontab`, директорій `/etc/cron.*` та активних сервісів `systemd`.
7. ** Цілісність та свіжі зміни** — пошук файлів у `/etc`, `/bin`, `/usr/bin`, змінених за останні 24 години, та верифікація цілісності конфігів пакетів (`debsums` / `rpm`).
8. ** Підсумковий звіт** — генерація зведеної таблиці статусів (`[OK]`, `[WARNING]`, `[CRITICAL]`) для швидкої оцінки готовності середовища до деплою.

## Інструкція із запуску

1. Надайте скрипту права на виконання:
   ```bash
   chmod +x security_check.sh
   ```

2. Запустіть аудит у потрібному режимі:
   * **Повна перевірка (за замовчуванням):**
     ```bash
     ./security_check.sh --full
     ```
   * **Швидка перевірка (без ресурсоємних опціональних модулів):**
     ```bash
     ./security_check.sh --quick
     ```
   * **Запуск із підвищеними привілеями (рекомендовано для перевірки `/var/log/btmp` та `debsums`):**
     ```bash
     sudo ./security_check.sh --full
     ```

## Аналіз результатів тестового середовища

Тестування проводилося на віртуальній машині під керуванням **Kali GNU/Linux Rolling** (ядро `7.1.5+kali-amd64`). За підсумками перевірки скрипт не виявив критичних вразливостей (`[CRITICAL]`), проте зафіксував два попередження (`[WARNING]`):

* **Розділ 4 (Мережа):** виявлено відкритий на всі інтерфейси (`0.0.0.0:22`) SSH-сервер, а також локальний X11-форвардинг (`127.0.0.1:6010`) і активне UDP-з'єднання DHCP-клієнта (`порт 68`). *Інтерпретація як DevOps-інженера:* для тестової VM це очікувана поведінка (SSH використовувався для адміністрування через MobaXterm), проте перед виходом у production я б обмежив доступ до 22-го порту через фаєрвол (UFW/Security Groups) лише для довірених IP-адрес та вимкнув автентифікацію по паролю на користь SSH-ключів.
* **Розділ 6 (Цілісність та свіжі зміни):** зафіксовано зміну файлу `/etc/resolv.conf` за останні 24 години. *Інтерпретація як DevOps-інженера:* це легітимна системна зміна, оскільки файл DNS-резолвера автоматично оновлюється мережевим менеджером під час отримання IP-адреси по DHCP при запуску VM. Виконувані файли у `/bin` та `/usr/bin` не змінювалися, додаткових користувачів із `UID = 0` чи world-writable файлів не знайдено.

**Висновок:** середовище не містить слідів компрометації та після базового тюнінгу SSH/фаєрволу готове до розгортання проєкту.
